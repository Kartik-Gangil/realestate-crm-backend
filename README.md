# Real Estate CRM Backend

## Run locally

```powershell
uv sync
uv run python manage.py migrate
uv run python manage.py runserver
```

## Authentication

Register or log in with email and password, then include the returned token in API requests.

```http
Authorization: Token <token>
```

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `POST` | `/api/auth/register/` | Register a user |
| `POST` | `/api/auth/login/` | Log in and obtain a token |
| `POST` | `/api/auth/logout/` | Invalidate the current token |
| `GET` | `/api/auth/me/` | Current user |
| `POST` | `/api/auth/forgot-password/` | Email a time-limited password-reset link |
| `POST` | `/api/auth/reset-password/` | Reset a password with `{ uid, token, new_password }` |
| `POST` | `/api/auth/change-password/` | Change the authenticated user's password |

## Organizations and access

Users may belong to multiple organizations. Every lead and follow-up call is organization-owned.

- `platform_superadmin`: Django user with `is_superuser=True`; has access to every organization.
- `platform_admin`: Must be promoted by a platform superadmin and explicitly granted organization access.
- `admin`: Full access to leads and organization members in their organization.
- `manager`: Full access to leads in their organization.
- `telecaller`: Sees only leads assigned to their membership and can log follow-up calls for them.

| Method | Endpoint | Access |
| --- | --- | --- |
| `POST` | `/api/platform/admins/` | Superadmin promotes a user using `{ "email": "..." }` |
| `GET/POST` | `/api/platform/organizations/` | Platform admin/superadmin lists or creates organizations |
| `POST` | `/api/platform/organizations/<slug>/access/` | Superadmin grants a platform admin explicit access |
| `GET/POST` | `/api/organizations/<slug>/members/` | Organization admin manages memberships |

Create an organization with an existing user's email as the initial organization admin:

```json
{
  "name": "Acme Realty",
  "slug": "acme-realty",
  "organization_admin_email": "admin@acmerealty.com"
}
```

## Tenant-scoped leads

All lead APIs require the organization slug in the path:

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `GET/POST` | `/api/organizations/<slug>/leads/` | List/create leads |
| `GET/PATCH/PUT/DELETE` | `/api/organizations/<slug>/leads/<id>/` | Retrieve/manage one lead |
| `GET/POST` | `/api/organizations/<slug>/leads/<id>/follow-ups/` | List/log separate follow-up calls |
| `GET` | `/api/organizations/<slug>/dashboard/` | Lead counts and latest call records |
| `GET` | `/api/organizations/<slug>/summary/` | Lead total and follow-up counts grouped by status |

Lead sources are limited to `facebook`, `instagram`, and `website`. Required create fields are `first_name`, `phone`, and `source`. Phone numbers are intentionally not unique.

To assign a lead, send an active organization membership ID:

```json
{
  "first_name": "Mayank",
  "phone": "+918882364687",
  "source": "facebook",
  "assigned_membership": 12
}
```

Follow-up notes remain separate from the lead:

```json
{
  "note": "Customer asked for a callback tomorrow.",
  "outcome": "callback",
  "status": "contacted"
}
```

Valid outcomes are `connected`, `no_answer`, `busy`, `callback`, `not_interested`, and `invalid_number`.
Follow-up statuses are `new`, `contacted`, `qualified`, `site_visit`, `negotiation`, `won`, and `lost`.

## Employee management

Employees are organization memberships with organization-specific profile and employment data. They do not share deactivation state across organizations.

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `GET/POST` | `/api/organizations/<slug>/employees/` | List/search/filter or create employees |
| `GET/PATCH/PUT` | `/api/organizations/<slug>/employees/<id>/` | Retrieve/update an employee profile |
| `POST` | `/api/organizations/<slug>/employees/<id>/activate/` | Activate an employee in this organization |
| `POST` | `/api/organizations/<slug>/employees/<id>/deactivate/` | Deactivate an employee in this organization |
| `POST` | `/api/organizations/<slug>/employees/<id>/reset-password/` | Organization admin issues a temporary password |
| `GET` | `/api/organizations/<slug>/employees/<id>/activity-history/` | Employee audit history |
| `GET/POST` | `/api/organizations/<slug>/departments/` | List/create departments |
| `GET/PATCH` | `/api/organizations/<slug>/departments/<id>/` | Retrieve/update a department |

Employee creation accepts `email`, `temporary_password`, `first_name`, and optional employment fields. Employee IDs are generated by the server as `EMP0001`, etc., unique within the organization. Admins can assign roles and access scopes; managers may create telecallers and update employee profile data.

## Environment set-up

Copy `.env.example` to `.env` and set the values for the environment. Generate a secret with
`python -c "import secrets; print(secrets.token_urlsafe(50))"`; a production deployment must set
`DJANGO_SECRET_KEY` and keep `DJANGO_DEBUG` off. With `DJANGO_DEBUG=1`, local host and origin
defaults are enabled and a temporary secret is generated when none is supplied. With debug off,
the backend refuses to start without a secret and enables the production security settings.

`DJANGO_ENV_FILE=none` disables env-file loading, while another value selects a specific env file
(relative paths are resolved from the Backend directory). The test suite reads `Backend/.env` too,
 unless a test explicitly sets `DJANGO_ENV_FILE=none`. Never commit `.env`; it is ignored by Git.

### File encryption key

Generate the key with `\.\.venv\Scripts\python.exe -c "import base64,os; print(base64.urlsafe_b64encode(os.urandom(32)).decode())"` and paste it directly into `.env`; never put it in chat or tickets. Losing it means losing every stored file. Back it up separately from the database and `private_media`; tests use their own key.
